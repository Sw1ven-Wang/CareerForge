# Lossless JD import and requirement lineage

This is an additive product path, not a rewritten evaluation answer file. The importer is deterministic. Requirement interpretation uses the configured `extract` model through the existing metered gateway. Source validation and the narrow qualifier contradiction checks do not prove semantic correctness or model quality.

## Public workflow

1. `POST /api/v1/jds` with `namespace_id`, `jd_id`, and exact `raw_text`. `job_title`, `source`, and `source_version` are nullable. Optional expected UTF-8 SHA-256, byte count, and identified paragraphs are checked, never repaired by rewriting source text.
2. `POST /api/v1/jds/extractions` with the returned `jd_revision_id`, the same private `namespace_id`, an authorized `funding_id`, and an `idempotency_key`. This admits a standalone `jd_extract` run with one model call. Inspect it through the normal run/result endpoints.
3. The result includes an immutable `goal_version_id`, requirements, logical groups, original source hash and coordinates, and a requirement-version hash. Reuse `goal_version_id` in a knowledge build, rather than extracting again. Alternatively, a knowledge build can accept `jd_revision_id` directly and reserve its extraction call up front.

The import document preserves UTF-8 bytes, whitespace, CRLF, Unicode, paragraph IDs, ordered offsets, and explicit null metadata. Character coordinates are absolute, half-open Unicode code-point offsets. Independent byte offsets make the distinction visible. Repeated text is legal when its occurrence is identified by offsets. Supplied paragraph lists must cover all non-whitespace source text.

Imports are immutable content-addressed revisions in the owner's private namespace. The same content and metadata are idempotent; a change produces a new revision. The source object, exact requirement envelope, frozen goal object and dependency edge are rechecked on reads, resume, model dispatch, research, and learning. Revocation and personal-data deletion block their dependents. No schema migration or new SQL table is required.

## Qualifiers and identity

The extraction schema keeps `depth` separate from `modality`. Unspecified depth remains null, and bonus/preferred status never lowers an explicitly stated target depth. Requirements retain their quoted source span, paragraph hash, JD revision and raw hash. Their IDs are generated by the server from the frozen source and interpretation, not from topic names or list positions.

Logical groups preserve AND, OR and unary NOT. AND/OR groups may nest and may span contiguous paragraphs. A direct NOT requirement is an explicit non-requirement, not an achievement. The service rejects unknown members, duplicate membership, cycles, out-of-scope spans and malformed provenance. Basic explicit contradictions such as turning an OR list into a flat AND, or turning an explicitly optional clause into a hard requirement, fail closed. These are bounded safeguards, not a general natural-language verifier.

A required OR and a preferred AND can legitimately refer to the same source sentence: one alternative is required, while experience with both is preferred. The alternative-to-mandatory-AND safeguard applies only to a direct group whose members are all required. It must not delete or reject the separate preferred combination. A regression checks this boundary after a real public-input extraction exposed the overly broad check; revalidating that response is a contract test, not a new model-quality result.

Research keeps all requirements visible. Bonus/preferred/non-required items do not become hard completion gates. One independently evidenced OR alternative can satisfy its group without pretending the remaining alternatives were evidenced. Unknown target depth is not replaced by a guessed level. Requirements, groups and learning text references carry `user_mastery_unchanged=true`; no learner profile or mastery state is written by import, extraction or research.

## Compatibility and limits

- Historical `jd_text` requests retain the original extraction schema, prompts, JSON source fingerprint and paid receipt replay. The new `jd_revision_id` path uses the `jd-import-1.6.6` and `jd-requirements-1.6.6` contracts. Old goal snapshots and old text-reference shapes are not upgraded on read.
- The original goal `content_hash` remains its historical canonical-JSON fingerprint. The new `raw_sha256` is separately and explicitly SHA-256 over untouched UTF-8 bytes. They are different identities and are never substituted for one another.
- Source text is untrusted data. Exact coordinates do not establish that an interpretation is semantically complete or correct. Independently judged model-quality tests and real provider/infrastructure tests must be reported separately.
- A failed extraction or unavailable provider is reported as failure, not filled with a regex-generated answer. Empty extraction is allowed when no technical requirement can be responsibly identified; it remains an unresolved research goal.
- This path does not infer mastery, run repository tests, publish research facts, or attest completion of the full eleven-stage business flow by itself.
